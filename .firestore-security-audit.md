# Firestore security model audit (working file; do not deploy)

## Authority model

- Firebase Authentication UID is the identity boundary.
- `admin`, `teacher`, and `student` authorization comes only from signed custom
  claims (`admin == true` or `role`). Firestore profile fields and browser
  storage are display data, never authority.
- The verified bootstrap administrator is limited to the institution account
  declared in the rules and requires `email_verified == true`.

## Collection access model

- `site`: public reads only for public CMS documents; admin writes.
- `users`: owner get/create/update with privilege fields forbidden; admin all.
- `messages`: anonymous validated create; admin read/delete; never client update.
- `admissions`: students can read only records bound to their UID; all student
  draft/submission/withdrawal writes pass through the authenticated server
  transaction. Staff access is claim-based. The deprecated
  `admissionApplications` path is admin-only.
- admission idempotency keys and rate limits are server-only; admission audit
  logs are server-written and admin-readable.
- `attendance`, `practicalsData`, `holidays`, `activityLogs`: teacher create and
  update, admin all; student reads only where explicitly owner-scoped.
- configuration, registers, finance, recycling, logs and import/history data:
  admin-only except read-only teacher academic configuration.
- `omr_registrations`: authenticated caller may create an immutable registration
  owned by their UID; admin manages. Public lookup must use the server endpoint.
- `studentVerificationIndex`: server/Admin SDK only.
- every unknown collection/subcollection: deny.

## Queries found

- admin messages ordered by `createdAt desc`.
- OMR equality lookups by board registration, form number, mobile and exam number.
- user equality lookups by email and teacher assignment fields (legacy; removed
  from authentication because list access to private profiles is unsafe).
- admissions equality lookups by dynamic legacy fields (admin only).

## Data assumptions

- Legacy academic documents have broad/dynamic schemas. Client writes are
  restricted to trusted staff claims and screened for credential/authority
  fields; new public/owner-created documents use strict validators.
- Existing records should be migrated to include `ownerUid` (and preferably
  normalized field names) before owner-facing reads are broadly enabled.
- Passwords, password hashes, payment secrets and authorization fields are not
  valid client-writable data.

## Devil's-advocate result

- Anonymous bulk/list access: denied except explicit public CMS reads.
- Cross-user profile/admission read: denied.
- Role/self-admin injection: denied by immutable/forbidden authority fields.
- Update bypass and schema pollution: public and self-service validators run on
  both create and update; messages/OMR have no client update path.
- Large public payload abuse: bounded strings, bounded key count, and fixed keys.
- Ownership hijacking: owner UID is required and immutable.
- Unknown/orphaned subcollections: default deny.
- Server lookup replay: HMAC-indexed lookup plus transactional server rate limit.
- Duplicate submissions and form-number races: stopped by an idempotency record,
  duplicate query, and form-number allocation in one server transaction.
- Browser PII persistence: admissions, user profiles and master registers are
  memory-only; Aadhaar, bank details and inline photos are excluded from drafts.
- Direct student mutation, forged status, owner UID, form number or timestamps:
  denied by Firestore rules and stripped/recreated by the server.
